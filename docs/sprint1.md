# Sprint 1 구현 범위와 검증 기준

| 단계 | 구현 | 검증 |
| --- | --- | --- |
| 1. 로컬 로그인 | 기존 설치 ID 재사용, FastAPI 루프백 콜백, PKCE·ID 토큰 검증, 비공개 저장 및 refresh token 교체 | 잘못된 state·발급자·nonce 거절, 동의 및 갱신 실패 처리 |
| 2. 소스 수집 | Git HEAD의 일반 파일만 임시 폴더에 복사, 제외 패턴·용량 제한 적용 | 미커밋 수정과 무시한 파일, 링크, 비밀 설정 제외 |
| 3. 정찰·계획 | Python 입력·DB·라우트·인증 단서와 주변 코드, 모델의 근거별 해석, 5종 점검 이유와 우선순위 | 없는 근거 인용·점검 누락/중복 거부, 소스 발췌 제한과 비밀값 마스킹 |
| 4. 검사·트리아지 | Semgrep·텍스트/AST 시크릿 검사, 모델의 keep/dismiss 및 심각도 재평가 | 표본 위치, 여러 줄·딕셔너리 시크릿, 원래 심각도·오탐 근거 보존, 집계 일치 |
| 5. 수정안 | 발췌의 대체 코드를 원본 문맥에 합쳐 Python 문법 검사 후 unified diff 생성 | SQLite 표본의 정상·따옴표·주입 문자열 동작, 불완전/비밀값 포함 코드 거부 |
| 6. CLI 완주 | 설치 가능한 명령, scan_result.json·report.md·이력 저장 | 새 Git 샘플을 설치된 CLI로 검사하고 보고서와 SQLite 확인 |

수동 전체 스캔을 대상으로 한다. 시크릿·SQL·XSS는 고정 정적 규칙으로 검사한다. 인증·인가 정책과 헤더·쿠키는 5종 계획에 항상 포함하되 **수동 확인 필요·미검사**로 표시한다. 동적 HTTP 검사는 계획서의 Sprint 4+ 범위다. SQL/XSS 규칙은 Python 표본에 한정되며 지원 소스가 없으면 별도 표시한다.

## 검증 경로

1. 설치 후 `vibescan login`은 등록한 환경의 클라이언트 ID와 설치 ID를 재사용한다. 인증 응답은 1회만 소비하며, 서명·발급자·대상·만료·nonce를 확인한 뒤 세션을 저장한다.
2. `vibescan scan <저장소>`는 HEAD를 먼저 고정한다. 루트·하위 Git 무시 규칙, 사용자 제외 규칙, 파일 크기(1 MiB) 및 전체 용량(64 MiB)을 적용한다. 임시 검사 대상으로 복사한 파일만 Semgrep에 전달한다.
3. 프로파일 단서는 로컬 AST에서 추출한다. 모델은 주변 코드로 입력·DB·라우트·인증 단서를 해석하고 점검별 이유와 관련 근거 ID를 작성한다. 검사 방식은 로컬 코드가 고정하며 모델이 검사 항목을 삭제하거나 임의 명령을 실행할 수 없다. 정적 검사 자체가 실패하면 성공 결과를 만들지 않는다.
4. 통합 테스트는 서명한 테스트 ID 토큰으로 FastAPI 콜백을 거쳐 실제 Semgrep을 실행하고, 모의 Responses 스트림으로 한국어 수정안이 결과 파일에 반영되는지 확인한다. 별도 검증 작업은 저장소 밖에서 설치된 CLI로 새 Git 샘플을 검사한다.

## 모델 문맥과 사용량

- 가명화한 파일·폴더 구조(최대 200개), 로컬 프로파일, 근거 ID와 코드 발췌(정찰 최대 12개·24,000자)를 전달한다.
- 발견 검토는 심각도 우선 최대 30건, 요청당 5건. 발췌는 최대 60줄/6,000자이며 문맥을 얻지 못하면 그 한계를 전달한다.
- 주석·독립 문자열 설명과 탐지된 비밀 리터럴을 제거한다. 같은 비밀값이 다른 파일에 반복되어도 가린다. 일반 코드 식별자·SQL·라우트 문자열은 문맥 분석을 위해 전송될 수 있다. 모든 비밀값을 보장하여 탐지하는 DLP 도구는 아니다.
- 모델 출력도 알려진 비밀값을 다시 가린다. 유효하지 않은 계획은 고정 계획으로 대체하고, 잘못된 검토 배치는 반영하지 않는다. 요청 실패 후 남은 모델 검토를 중단하며 정적 결과와 참고 예시는 보존한다.

## 판정과 수정안의 의미

- 오탐 후보는 삭제하지 않고 `dismissed`와 `original_severity`, `triage_reason`을 저장한다. 열린 발견의 점수·집계에서 제외하되 보고서에 별도 표시하므로 개발자가 판정을 확인할 수 있다.
- 정적 단서만으로 실제 악용을 확정할 수 없어 모델은 `Confirmed`를 부여할 수 없다.
- 수정안은 마스킹된 코드에 대한 **동작 검증 전 제안**이다. 원본 파일을 수정하거나 모델 코드를 실행하지 않는다. Python 문법 통과가 업무 로직·보안 효과의 보장은 아니다.
- DB 종류나 문맥이 부족하면 대체 코드는 생성하지 않고 확인할 조건을 설명한다. 코드가 없거나 검증에 실패하면 **로컬 참고 예시**로 표시한다.
- 발견이 0건이어도 미검사 항목과 범위 제한을 보여 준다. 검사할 파일 자체가 없으면 성공 보고서 대신 오류를 반환한다.

## 검증 범위

GitHub Actions는 Windows·Ubuntu에서 전체 테스트와 저장소 밖의 설치형 CLI를 검증한다. CI 로그인·모델 응답은 모의 공급자로 계약을 검사하며 실제 계정 토큰이나 구독을 사용하지 않는다.

2026-11-18에는 실제 구독 모델로 새 응답 형식을 검증했다. 동일한 샘플 HEAD에 대해 코드 근거 5개, 점검 계획 5종, 상세 검토 3/3건과 XSS 수정 diff를 확인했다. 모델은 DB 드라이버가 불명확한 SQL 수정 코드는 보류하고 조건을 설명했으며, 시크릿 후보는 근거와 함께 High에서 Low로 재평가했다. 검증 결과 ID는 `366b54655da94cd993b0a67a9fb55bdb`다.

이 실계정 검증에서는 로컬 Semgrep 실행 제약 때문에 파일 내용과 위치가 동일함을 확인한 기존 Semgrep 표본 결과를 사용했다. 실제 Semgrep 바이너리를 포함한 전체 흐름과 설치형 CLI는 Windows·Ubuntu CI에서 별도로 검증한다. 모델이 만든 코드는 자동 실행하지 않았으며, SQL/XSS 수정의 동작 테스트는 작성된 테스트 표본으로 수행했다.

대시보드, GitHub clone, hook/diff 자동 스캔과 HTTP 동적 검사는 이번 작업에 포함하지 않는다.
